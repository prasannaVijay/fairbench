Systems," lives in this repository. This is the `ch10` branch: `main` plus the
trace store, the three-layer regression investigation, the measurement-quality
targets, and this map.

## Run an investigation

```bash
pip install pydantic pyyaml numpy scipy

python ch10/investigate.py --list                 # what the trace store holds
python ch10/investigate.py classifier-shift       # the metric moved, the model did not
python ch10/investigate.py model-regression       # the model moved, the classifier did not

# any pair of runs, optionally narrowed to a slice
python ch10/investigate.py --current soccer_2026_w14 --prior soccer_2026_w13 \
    --metric RSI_gender --partition role=goalkeeper

# the measurement-quality checks
python ch10/investigate.py --quality ch10/fixtures/measurement_quality_w14.yaml
python ch10/investigate.py --quality-from-traces \
    --current soccer_2026_w14 --prior soccer_2026_w13

python ch10/make_fixtures.py                      # regenerate the fixtures
```

Everything runs against `ch10/fixtures/`, so none of it needs an API key, a
network connection, or configuration. The two modes exit differently on purpose:
an investigation always exits zero because it is a diagnosis and not a decision,
and a measurement-quality check exits non-zero on a breach so that it can gate a
pipeline.

## What the code is for

`ch10/regression_report.py` is the function the chapter prints, with the four
helpers it names. `investigate_regression` walks the three layers in one call
and returns a `RegressionReport` whose fields map onto them: `partitioned_delta`
is the aggregate check, `distribution_shift` the distributional one,
`top_contributing_prompts` the instance layer, and `classifier_confidence_shift`
the guard that separates a real model regression from a classifier that simply
changed its mind. Two design decisions carry most of the weight.

The distributional layer reads a **pinned reference probe** rather than the
production classifier. Holding one perception model at a fixed version across
runs is the only reason the distributional signal stays still when the
production classifier is upgraded, and without that independence the guard could
not separate the two hypotheses at all.

The scenario value is a **mean across prompts, not across records**. Under a
record-weighted mean, a prompt that lost most of its replicates to
low-confidence exclusions quietly loses most of its vote and the aggregate moves
for a reason unrelated to the model or to any prompt's score. Weighting prompts
equally confines the effect of exclusions to the values they actually changed,
and `exclusion_rate` reports them in their own right. The per-prompt
contributions then sum exactly to the scenario delta, so the instance layer is a
decomposition of the movement rather than a heuristic ranking.

`ch10/trace_store.py` is the trace format and a newline-delimited-JSON store,
one file per run. `metric_contribution` is recorded at the grain at which the
metric is defined: a divergence such as RSI has no value for a single generated
image, so every replicate trace of a prompt carries that prompt's divergence,
while HSI is a mean of per-output severity scores and does decompose to the
individual replicate. Both metrics sit in the fixtures, which is the clearest
illustration of why that grain is a property of the metric and not of the format.

`ch10/measurement_quality.yaml` carries the chapter's
`measurement_quality_metrics` block. `ch10/measurement_quality.py` parses its
targets, checks an observed report against them, and reports each breach with
the action the block prescribes; a target with no observed value lands in
`not_measured` rather than passing quietly. It also carries estimators, and two
of the three are approximations that read more favourably than the measurement
the target is written against: `bootstrap_metric_sd` resamples within one run
and cannot see day-to-day variation in the generation API, and
`power_from_traces` estimates power after the fact from the same data it will be
used to judge. Both say so in their docstrings and in the provenance notes the
generated report carries.

## The fixtures

`ch10/fixtures/traces/` holds four simulated runs forming two investigations of
the same size and direction, separated only by which layer moved.

| Runs | Model | Classifier | What moved |
|---|---|---|---|
| `soccer_2026_w13` → `soccer_2026_w14` | v4.2 (outputs served from cache) | v3.1 → v3.2 | The classifier. RSI_gender rises 0.311 → 0.347 because v3.2 is unsure about padded-kit goalkeeper and striker frames, excludes them from scoring at 15% against 1%, and the exclusions skew the surviving sample |
| `soccer_2026_w20` → `soccer_2026_w21` | v4.2 → v4.3 | v3.3 (unchanged) | The model. RSI_gender rises 0.308 → 0.354, the pinned probe sees the output distribution shift, and classifier confidence does not move |

Because w14 re-uses w13's cached outputs, the two runs share an evaluation set,
which is what an inter-rater kappa across the classifier boundary needs: a kappa
computed over two different sets of generated images measures how alike the
samples were and says nothing about the two classifiers. That kappa comes back
at 0.55 against a target of 0.80, which is the chapter's argument in one number.

These are **simulated** traces. They are faithful to the mechanism the chapter
describes and they are not measurements of any real model, so no conclusion
about a real system should be drawn from the values in them.
